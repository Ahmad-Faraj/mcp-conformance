We probed \Nprobed{} servers: the complete eligible frame, a census rather than a
sample.

\subsection{RQ1: Runnability and the startup funnel}
\HandshakeCountCorr{} of \Nprobed{} servers (\HandshakeRateCorr{}) complete the MCP
handshake once the entry-point artifact described in Section~\ref{sec:rq5} is
corrected; the uncorrected census figure is \HandshakeRate{}. Roughly two in five
never serve the protocol at all. Figure~\ref{fig:failures} classifies those failures
by cause.

Two distinctions matter for reading that figure. First, servers that merely need
credentials or configuration are counted separately from servers that crash;
conflating them would blame the ecosystem for what is a documentation gap. Second,
most failures occur \emph{after} a successful install: the package downloads, then
the process crashes, hangs, or exits without speaking the protocol. The failure is in
the software, not the packaging. No prior work has measured how often
registry-published servers fail to start, and because we census the entire eligible
frame, these are population counts rather than estimates.

\subsection{RQ4: The spec--practice divergence and its cause}
\ErrAsResultRate{} of responding servers reported a call to a non-existent tool as
an \texttt{isError} tool-execution result rather than the JSON-RPC protocol error the
specification illustrates. As established in Section~\ref{sec:threats}, we treat this
as a divergence rather than a violation, because the specification uses no RFC-2119
keyword here. To explain its near-universality, we attribute each server to its SDK
from package metadata (Figure~\ref{fig:sdk}, Table~\ref{tab:sdk}). The behavior
tracks the SDK: the
official TypeScript and Python SDKs and the popular FastMCP framework all default to
it. A small number of TypeScript-SDK servers emit the protocol error, showing the
conforming behavior is achievable within the SDK but is not its default. We confirm
this directly against the official reference servers, which exhibit the same
divergence.

Our attribution recognizes a fixed list of known SDK package names, so the residual
\textsf{no-known-SDK} category must not be read as ``hand-rolled.'' Inspecting a
random sample of that category, we find roughly two thirds in fact depend on an MCP
framework outside our list---several third-party wrappers, each used across dozens of
servers by a single publisher---most of which themselves build on an official SDK.
That category therefore supplies no independent evidence and we do not treat it as
such; what it does indicate is that the monoculture extends \emph{beyond} the
official SDKs, into a layer of third-party wrappers that inherit their defaults. The
finding is not that thousands of authors independently erred, but that a handful of
SDK defaults, propagated both directly and through wrappers, set ecosystem behavior.

\subsection{RQ5: Correlates}
\label{sec:rq5}
We test whether runnability and conformance correlate with the package registry
(Figure~\ref{fig:byregistry}). Runnability differs sharply: npm servers complete a
handshake far more often than PyPI servers (\NpmRate{} of \NpmN{} vs.\ \PypiRateRaw{}
of \PypiN{}; two-proportion $z=12.1$, $p<10^{-3}$). Conformance does not differ: the
error-as-result divergence appears in $87.7\%$ of responding npm servers and $90.2\%$
of responding PyPI servers. This is what RQ4 predicts. Because the divergence is
inherited from the SDKs, and both language ecosystems' SDKs share the same default,
the registry a server ships on changes whether it \emph{starts} but not whether it
\emph{conforms}.

Part of this gap is an artifact of our own launcher, and we corrected it rather than
reporting it. We launch PyPI servers as \texttt{uvx <package>}, which resolves only
if the package's console script is named after the package; npm's \texttt{npx}
resolves the entry point from \texttt{package.json} and has no such requirement.
\NEntrypointBlocked{} PyPI servers---\EntrypointBlockedPct{} of the PyPI
population---installed successfully but were never launched for this reason alone. We
re-probed all of them with the entry point resolved from the installed package
metadata. \EntrypointRecovered{} (\EntrypointRecoveryRate{}) then completed a
handshake; the rest failed for reasons unrelated to naming (Python exceptions, hangs,
undeclared configuration). Correcting for this raises PyPI runnability from
\PypiRateRaw{} to \PypiRateCorr{} and the overall census figure to
\HandshakeRateCorr{}, which we report as the headline throughout. The npm--PyPI gap
narrows from \GapRaw{} to \GapCorr{} percentage points but remains large: the gap is
real, not a measurement artifact.

The entry-point problem is itself an ecosystem finding. Registry metadata does not
record a server's entry point, so a client following the registry alone cannot launch
a fifth of published PyPI servers---and once the entry point is resolved, nine in ten
of those servers still fail to start. Discoverability and runnability are distinct
failures, and the registry surfaces neither.
