\paragraph{The specification and the SDKs}
For whoever decides SEP-2145, accepting it would mostly document practice that
already exists. SEP-1303 reclassified input validation failures as tool execution
errors, arguing that a model can only correct an error it sees~\cite{sep1303}, and
SEP-2145 proposes the same for unknown tools~\cite{sep2145}. \ErrAsResultRateCl{} of
responding servers already return \texttt{isError} for an unknown tool. Rejecting the
proposal would leave nine in ten responding servers non-conformant by example, and we
do not expect \ErrAsResultCount{} servers to be changed by hand. The remaining
servers do not form one alternative either: \UnknownProtoErrCount{} emit a protocol
error, \UnknownWrongCodeCount{} emit a different code, and \UnknownProseCount{} report
the failure only in the text of a successful result.

The behavior tracks the SDK rather than the author. The official TypeScript and
Python SDKs and the third-party wrappers built on them all default to
\texttt{isError}. So \ErrAsResultRateCl{} should not be read as consensus among server
authors. It measures SDK adoption. The practical consequence is that the lever is a
small number of libraries, and a change there reaches thousands of servers at once,
in either direction. Section~\ref{sec:rerun-top} shows the other direction: one breaking
release of the Python SDK stopped \PySDKLostRate{} of the servers built on it, none of
whose authors changed anything.
The limit of that lever is visible here too: the unknown-tool fix recorded on the
TypeScript SDK's tracker in March 2026 did not move the rate, and the error still
arrives inside a successful response.

\paragraph{Silent execution is a different kind of finding}
The unknown-tool case is a disagreement about the error channel, and the client is
still told the call failed. Here the client is told nothing. Input validation is an
explicit MUST in the specification with no pending proposal to relax it, so
this cannot be framed as the specification lagging practice. \SilentExecTS{} of the
\NSilentExec{} are built on the official TypeScript SDK, whose low-level
\texttt{Server} API publishes a tool's \texttt{inputSchema} and does not enforce it
(Section~\ref{sec:consequences}). That looks like a library gap rather than
\NSilentExec{} separate author mistakes.

The client can no longer tell the result apart from a correct one. There is no error
code, no \texttt{isError} flag, nothing to branch on. An empty feed, returned for top
stories with a limit of \texttt{"not-a-number"}, is indistinguishable from a day with
no stories, so there is no retry, no argument repair, and no warning to the user. \NSilentExec{} is a
lower bound: we counted any error-like token in a reply as a report.

\paragraph{Startup failure and what a registry could do about it}
Being published does not mean it runs, and the registry carries no signal for it.
Pimentel et al. report the same for notebooks~\cite{notebookreproducibility}, as do
Ibrahim et al. for images that share a name on Docker Hub~\cite{dockerhubimages}. The
registry should attempt a handshake at publish time and show the outcome: flag it,
not delist it. It should also record the entry point and the required configuration.
\NEntrypointBlocked{} PyPI servers could not be launched from registry data alone,
and \NNeedsConfig{} failed for no reason other than undeclared configuration. We ran
this check across \Nprobed{} servers, so it is feasible at registry scale.

\paragraph{What running the servers shows that reading them cannot}
Studies that analyze MCP servers from source or
metadata~\cite{mcpfirstglance,mcplandscape} cannot observe any of these failures.
Observing them needs execution. In line with Ait et al. on Hugging Face Hub~\cite{huggingfacehub}, the registry as a
data source is also less reliable than it looks. Our own launcher undercounted
runnability until we corrected the entry-point problem and passed the launch arguments
that registry entries declare: on PyPI, \PypiRateRaw{} uncorrected against
\PypiRateCorr{} after.

The two package registries separate the two questions. Runnability differs by
\GapCorr{} percentage points, \NpmRateCorr{} against \PypiRateCorr{}, while conformance
among the servers that do run does not. Packaging is per-ecosystem. Protocol behavior
is per-SDK. Improving conformance means fixing a few libraries and improving
runnability means fixing thousands of packages, which are very different amounts of
work.

\paragraph{A moving specification}
The lifecycle we measure is being retired. Revision 2026-07-28 drops the
initialization handshake and negotiates a version on every request instead, with an
optional \texttt{server/discover} call for clients that want to ask up
front~\cite{mcpversioning}. Our population sits well behind that boundary:
\PctVerOffered{} of responders settled on 2025-06-18, and \NVerDowngraded{} answered
with something older still.

The revision did not wait for authors to adopt it. The official Python SDK released
2.0.0 on the same day, implementing the new revision and renaming a class many servers
import~\cite{pysdk200}, and that release is the one the September re-run found in the
output of the servers it lost (Section~\ref{sec:rerun-top}). For a server that
declared the SDK as a range, the new revision arrived as a dependency update its
author never chose, and for most of those servers it arrived as a failure to start.
The July census therefore records this ecosystem immediately before the revision
reached it, and the re-run records its arrival. Behavior measured from now on reflects
that transition, and the July census is the baseline against which it can be
compared.

\paragraph{Recommendations}
The specification should accept SEP-2145, state it with an RFC-2119 keyword instead
of an example, and add the unknown-tool case to the conformance suite so that it is
tested.

SDK authors should validate \texttt{tools/call} arguments against the declared
\texttt{inputSchema} by default, in the low-level \texttt{Server} API as well, and
check the tool name against \texttt{tools/list}. Most authors never change the
default, so the default is the behavior.

Agent framework authors should not treat a result without \texttt{isError} as
correct. They should validate arguments client-side against the schema before the
call, and treat a server as untrusted until it completes a handshake.

Registry maintainers should run a handshake at publish time, show the result, and
store the entry point and the required configuration in the listing.
