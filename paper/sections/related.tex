\subsection{The Model Context Protocol}
MCP standardizes how LLM agents discover and invoke external tools. A client and
server negotiate a protocol version and capabilities during an \texttt{initialize}
handshake. The client can then list tools (\texttt{tools/list}) and invoke them
(\texttt{tools/call}). Messages follow JSON-RPC 2.0, including its error-object
semantics and its reserved error codes. Most deployments run the server locally over
stdio, where stdout carries protocol traffic and nothing else. The specification is
versioned by date, and servers may negotiate down to a version they support.

\subsection{Static studies of the MCP ecosystem}
The ecosystem has been studied at scale, but never by running it.
Health-and-maintainability work analyzes source and metadata for roughly 1,900
servers using static scanners and code-smell detectors~\cite{mcpfirstglance}, while
registry measurement crawls several marketplaces and characterizes scale,
maintenance and supply-chain concentration across some 8,000 servers, all of it
derived from listing metadata rather than from anything the servers
do~\cite{mcpcrawler}. Fault taxonomies take a third route and mine GitHub
issues~\cite{runtimefaults,realfaults}. They find that tool faults and
schema-enforcement problems dominate what users actually hit, which is the same pair
our harness measures directly rather than through bug reports. None of this work
executes a server.

\subsection{Execution-based work is security-focused}
Some prior work does execute MCP servers, but it targets security rather than
conformance and it does so on small or synthetic populations: sandboxed behavioral
scanners and taint-style analyzers hunt vulnerabilities in curated or deliberately
vulnerable server sets~\cite{sandboxscan,viper}, a security-invariants benchmark
avoids live third-party execution altogether in favor of fixtures and a
40-repository metadata sample~\cite{securityinvariants}, and malicious-server
detection and authentication studies scope to security
surfaces~\cite{maliciousmcp,remoteauth}. Conformance is a different question:
whether a server that is neither malicious nor vulnerable does what the
specification says. That question is unaddressed.

\subsection{The specification's own error-handling debate}
The categorisation this paper measures is under active revision. SEP-1303, accepted
and reflected in the current specification, moved tool input validation errors out of
protocol errors and into tool execution errors, reasoning that a language model can
self-correct only from an error that reaches its context~\cite{sep1303}. SEP-2145,
open at the time of writing, extends the same treatment to tool resolution failures,
including unknown tools, and states its purpose as aligning the specification with
existing Python and TypeScript SDK behaviour~\cite{sep2145}. Both proposals argue from
implementation practice. Our contribution to this debate is not an opinion about which
mechanism is correct; it is the number that tells the participants what fraction of the
deployed ecosystem their proposed alignment already describes.

Concurrent with this work, a practitioner census posted to the same proposal probed
roughly 10,500 \emph{remote} registry endpoints, harvested their tool lists, and
reported that \(88.8\%\) of mutating tools declare no output schema at all, arguing
that the proposal's output-validation clause is inert for most of the write
surface~\cite{siliroid2026census}. That measurement and ours are close to disjoint.
It probes hosted HTTP endpoints and reads declared metadata; we install and execute
local stdio servers and test behaviour against inputs. It addresses the
output-validation clause; we address tool resolution and input enforcement. The two
agree on the underlying point, which is that this proposal has been debated without
deployment data, and both supply some.

\subsection{Conformance tooling and the gap we fill}
The protocol maintainers ship a conformance suite. It exercises the official SDKs in
continuous integration, and it has never been pointed at the deployed ecosystem. The
community has begun proposing a pre-publish conformance checklist for server authors,
which is demand for precisely this measurement. Practitioner audits circulate
striking headline numbers---that most listed servers are unmaintained, for
instance---without published methodology, data, or protocol-level testing. Ours is,
to our knowledge, the first reproducible conformance measurement of this ecosystem
that installs and executes the servers themselves and tests their behaviour against
adversarial inputs, released with an open harness and dataset. It follows a long line of
empirical software-engineering studies that execute a population to find out how it
behaves, rather than how its documentation says it should.
